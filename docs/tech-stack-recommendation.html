Tech Stack: Should You Change It?

An honest assessment of Java 21, Spring Boot 3.4 and Spring AI for the PersonaVault knowledge vault.

Verdict

Stay on Java 21, Spring Boot 3.4 and Spring AI. No change is needed.

The stack is not the bottleneck. The differentiator is the design, not the language or framework.

This started as a practice project, but the stack you chose happens to be genuinely well suited to where the product is heading. Below is the reasoning, including where the friction really is and which small additions are worthwhile.

Why the current stack fits the vault

Requirement to existing capability
RequirementWhy Java and Spring Boot already win
Local-first, single-user, offlineOllama, PGVector and a local filesystem are stack-agnostic; Spring configuration and environment handling are mature.
Data integrity: facts, provenance, contradictionsJPA, Flyway and Postgres transactions are exactly the right tools. This is relational work, and Java's typing discipline helps enforce it.
Schema-driven extraction across many domainsSpring dependency injection with list injection, already used for the notification channels, is a clean polymorphism mechanism: one interface, many implementations.
Async pipelines: extraction, wiki compilationThe async executor configuration is already in place and extends naturally to the wiki compiler.
Scheduled jobs: renewals, nightly recompileThe existing scheduled checker pattern covers it.
Testability and quality gatesThe JaCoCo, SpotBugs, PMD and Checkstyle setup is a real asset for a trust-first product.
Long-lived personal dataThe JVM and Postgres are boring, stable and will still run in ten years, which suits a vault you keep.

Where the friction actually is

  1. Authoring tooling, not the language. The assistant's file-writing tools strip Markdown formatting, so documentation is being authored as HTML. This is an environment quirk, not a product or stack problem.
  2. Model-orchestration ergonomics. Python has more tutorials, but Spring AI 1.0 is stable and covers advisors, vector stores, structured output and tool calling. Switching would mean rewriting working code for marginal gain.
  3. Prompt iteration speed. Slightly faster in notebooks, but prompts can be prototyped in any tool and ported back.

What not to do

  • Do not rewrite in Python or Node. You would lose the quality gates, the injection-based polymorphism and months of working code.
  • Do not add a graph database or a second datastore. Postgres covers the entity and fact model.
  • Do not move to a managed vector database. It violates the local-first requirement.

Summary

If this were a throwaway prototype, Python would be the faster choice. For a long-lived, trust-critical personal vault with heavy relational data, Java, Spring Boot and Postgres are arguably the better choice, and you already have them.

Keep the stack, add the four libraries above as their decision records land, and let the vault design be the differentiator.
